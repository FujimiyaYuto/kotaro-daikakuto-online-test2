# コタロの大格闘 Online — Online Phase 2 完成報告

「遠隔プレイヤーによるキャラクター操作実験」。GUEST がルミポを左右移動・ジャンプで操作し、HOST のゲーム内で既存の物理のまま動くところまで。
攻撃・ダメージ・KO・勝敗の同期、予測、ロールバックは実装していません。

## 0. 全体の流れ
1. Phase 1 と同じ：HOST がルームを作る → GUEST がコードで参加 → 接続成功
2. 接続画面に「操作実験（Online Phase 2）」欄。HOST だけ「操作実験を開始」ボタン
3. HOST が押す → GUEST へ `ms`（開始）→ GUEST はゲーム画面へ切り替えて `mr`（準備完了）を返す → HOST もゲーム画面へ
   （4 秒以内に返事が無ければ開始しない。片方だけゲーム画面にならない）
4. 両方の画面に「ONLINE MOVE TEST」表示。どちらかの「実験を終了」→ `me` → 両方とも接続画面へ戻る（接続は維持）

## 1. ネットワーク入力の構造（GUEST → HOST）
- 入力元は既存の InputManager（キーボード：A/D・←/→・Space/W/↑、スマホ：専用パッド）。GUEST はゲームを進めない代わりに、固定ステップ（60 回/秒）ごとに `InputManager.poll()` で入力を読む。
- 送るのは「現在の入力状態」：`{"t":"mi","s":入力番号,"l":0/1,"r":0/1,"j":0/1,"jp":ジャンプ押下の累計,"ts":送信時刻}`（約 60 バイト）
  - `l` / `r` / `j` … 今押しているか（離した状態も 0 として届く）
  - `jp` … ジャンプを「押した瞬間」の累計回数。押しっぱなしでは増えない
- 座標・速度・ダメージなどは一切送らない（HOST も受け付けない）。

## 2. 入力送信 Hz
- 入力が変わった時：その固定ステップですぐ送る（最大 60 回/秒。実際は押した・離した瞬間だけ）
- 変わらない間：100ms ごと（10Hz）に同じ状態を再送（生存確認と取りこぼし対策）
- 実測：止まっている間・押しっぱなしの間は 約 10Hz、操作中は変化の数だけ増える。
- 30Hz で同じ内容を送り続ける方式にしなかった理由：押した瞬間の遅れ（最大 33ms）が無くなり、通信量も減るため。再送があるので、将来順序保証なしの通信に変えても状態は 100ms 以内に正しくなる。

## 3. HOST authoritative の実装
- 操作実験の間だけ、ルミポの `controller`（CpuController）を `RemoteInputController` に差し替える（終了時に同じオブジェクトを戻す。CPU AI のコード・設定には触れない）。
- `RemoteInputController.poll()` は既存の CpuController と同じ形のコマンド（`moveX`・`held.jump`・`pressed.jump`）を返すだけ。ルミポは既存の `Fighter.update()` で、加速・減速・重力・ジャンプ・空中制御・コヨーテタイム・ジャンプバッファ・空中ジャンプ・ジャンプカット・床判定・一方通行床・衝突のすべてを通って動く。新しい物理は作っていない。
- コタロは HOST 本人の InputManager のまま（攻撃・必殺・泡・ガードだけを外すフィルターを通す）。
- 攻撃系は両者とも入力が届かないため、当たり判定が発生しない（「片方だけ当たった」は起きない）。キーボードの J/K/L/I・R（リセット）・Enter は止め、スマホの攻撃ボタンは隠す。
- ストックは Infinity（場外に落ちても既存ルールで復帰するだけ。KO・勝敗は発生しない）。カウントダウンは使わない。
- ゲーム本体のファイルは変更せず、`game.step` をこのゲームのインスタンスだけ差し替え（HOST：元の step の後に状態送信、GUEST：入力送信と補間表示）。終了時に削除して元に戻す。

## 4. HOST → GUEST の状態同期
- `{"t":"st","s":状態番号,"h":HOST のゲーム内時刻,"w":送信時刻,"a":反映済みの最新入力番号,"f":[[コタロ],[ルミポ]]}`
- 各キャラ：`[x, y, vx, vy, 向き, フラグ(場にいる・接地・状態), 無敵の残り秒]`（約 150〜180 バイト）
- 送信：HOST のゲームの固定ステップ 2 回に 1 回 = **30Hz**（描画のフレームレートとは独立）。
- 送るのは画面表示に必要な最小限だけ。GUEST はこれを表示するだけで、勝敗などを自分では決めない。

## 5. GUEST の表示補間
- 受け取った状態を「HOST のゲーム内時刻」で並べ、**70ms 遅らせた時刻**の前後 2 つから位置を線形補間（30Hz の状態約 2 個分の余裕）。
- HOST 時刻と自分の時計の対応は、届いた状態から推定（早く届いた値に素早く寄せ、遅れた値にはゆっくり寄せる）。
- 次の状態が遅れた時は、速度で最大 100ms だけ先へ伸ばし（外挿）、それ以上は止めて待つ。
- 400 以上離れた 2 状態の間（リスポーンなど）は補間せず切り替える。
- 向き・接地・状態は近い方の状態を使う。描画は既存の `Fighter.draw()` とカメラをそのまま使う。
- 予測（client prediction）はしない。診断表示に「予測なし」と明記。

## 6. ジャンプ入力
- GUEST：`InputManager` の「押した瞬間」（既存の pressed）を数え、`jp` を 1 増やす。押しっぱなしでは増えない。
- HOST：`jp` が増えた分だけ「押した瞬間」を 1 ステップずつ `pressed.jump` として渡す（最大 2 回分を保留）。`held.jump` は `j` のまま。
- これで既存のジャンプバッファ・コヨーテタイム・空中ジャンプ（押した瞬間のみ）・ジャンプカット（早く離すと小ジャンプ）がそのまま働く。
- 確認：押しっぱなし 1.8 秒 → ジャンプ 1 回、短く押す → 小ジャンプ（60 vs 通常 207）、2 回押す → 空中ジャンプ（350）。

## 7. sequence 管理
- 入力 `s`：GUEST が 1 ずつ増やす。HOST は今までより大きい番号だけ受け付け、古い・重複・逆順は捨てる（操作状態が巻き戻らない）。`jp` が減る入力も捨てる。
- 状態 `s`：HOST が 1 ずつ増やす。GUEST も同様に古い状態を捨てる。
- 状態の `a`（HOST が反映した入力番号）で、GUEST は「入力 → HOST で反映 → その結果が届く」までの時間を測る。

## 8. 無通信時のニュートラル処理・切断
- HOST：新しい入力が **500ms** 届かなければ、ルミポの入力を left/right/jump すべて 0 に（保留中のジャンプも捨てる）。再送が 10Hz なので約 5 回分の取りこぼしで発動。
  - 確認：RIGHT を押したまま GUEST の送信を止める → 約 440ms でニュートラル、ルミポ停止。接続は維持。
- GUEST のタブが裏に回る・画面ロック → GUEST の送信が止まる → 同じくニュートラル。
- 切断（相手のタブを閉じた・更新した・10 秒無受信・切断ボタン）：操作実験を即終了 → 入力をニュートラル → 差し替えを元に戻してタイトル状態 → 接続画面に「接続が切れました」と「メニューへ戻る」。CPU には切り替えない。

## 9. スマホ操作
- GUEST：左下に LEFT / RIGHT（指を左右に滑らせると切り替わる）、右下に JUMP。Pointer Events を指ごとに追跡するので「LEFT を押したまま JUMP」が可能。既存のボタンと同じ見た目・大きさ（`--btn`）。
- HOST：既存のスティック + ジャンプボタン（攻撃系ボタンは隠す）。
- ゲーム画面は横向き前提（縦では既存の「横向きにしてください」案内）。接続画面は Phase 1 のとおり縦横どちらでも可。
- 診断表示はスマホでは最初は畳み、「診断」ボタンで開く。

## 10. セキュリティ
- `mi`：`s` は 1 以上の整数、`l` `r` `j` は 0 か 1、`jp` は 0 以上の整数、`ts` は数値。それ以外は破棄。余分なキー（x・y など）はコピーしないので使われない。
- `st` は GUEST 側でしか受け付けない（HOST に送られても破棄）。配列の長さ・各値の範囲を検証。
- HOST は 1 秒あたり 90 件を超える入力を無視（全体の受信上限 240 件/秒も Phase 1 のまま）。ゲームは 1 ステップに 1 回入力を読むだけなので、大量に来ても壊れない。
  - 確認：400 件を一度に送っても、ゲームは継続・接続も維持・その後も普通に操作可能。
- 表示は textContent のみ。

## 11. GUEST 本人の画面での遅延の構造（理論）
```
キーを押す
 └①  次の固定ステップで読む ……………………… 0〜17ms（平均 8）
 └②  すぐ送信 → HOST へ届く（片道） ……………… Ping の半分（遠隔実測 30ms → 約 15ms）
 └③  HOST の次の固定ステップで反映 ……………… 0〜17ms（平均 8）  ※ここで HOST の画面のルミポが動き出す
 └④  次の状態送信（30Hz）まで ……………………… 0〜33ms（平均 17）
 └⑤  GUEST へ届く（片道） ……………………………… Ping の半分（約 15ms）
 └⑥  表示補間の遅れ …………………………………… 70ms（固定）
 └⑦  次の描画フレーム ………………………………… 0〜17ms（平均 8）
```
- 合計の目安：**Ping + 約 110ms**（平均）。遠隔実測 Ping 30ms なら **約 140ms**（最短 約 100ms〜最大 約 185ms）。
- HOST の画面でルミポが動き出すまで：①+②+③ ≈ **Ping/2 + 16ms**（30ms なら約 30ms）。
- 診断表示の「入力→HOSTで反映→受信」が ①〜⑤ の実測値、「体感の目安」は それ + 70ms + 8ms。
- 加速があるため、見た目で「動いた」と感じるのはさらに 1〜2 フレーム後。

### 擬似遅延での実測（同一 PC、ローカル）
| 条件 | 押す→HOST で動き出す | 押す→GUEST 画面で動き出す | 入力→反映→受信 平均/最大 | 1 フレームの移動量 中央値/最大 |
|---|---|---|---|---|
| Ping 約 30ms | 52ms | 126ms | 65 / 115ms | 5.6 / 7.5 px |
| Ping 約 100ms | 78ms | 188ms | 125 / 205ms | 5.5 / 9.4 px |
| Ping 約 200ms＋時々 +150ms | 139ms | 302ms | 240 / 376ms | 5.6 / 7.5 px |

- どの条件でも表示は滑らか（止まる・飛ぶフレームなし）。遅延だけが Ping に比例して増える。
- Ping 100ms を超えると GUEST 本人の操作は「遅れて付いてくる」感じになる見込み → Phase 3 以降で予測を検討する材料。

## 13. CPU 対戦が変わっていないこと
- ゲーム本体の 22 ファイル・`style.css`・素材は v1.0 とバイト単位で同一。
- 乱数を固定し v1.0 と実験版で EASY / NORMAL / HARD / CHALLENGE を最後まで実行 → 全フレームの記録・決着ステップ数・勝敗が完全一致。
- さらに「操作実験を開始 → ルミポを遠隔入力で動かす → 終了」をした後に同じ試合を実行しても完全一致（差し替えが残らない）。
- 画面操作（タイトル → 難易度 → 対戦 → 勝敗 → もう一度 → タイトル）・音声も確認。
- オンライン用のコードは Math.random を使わない（CPU の乱数に影響しない）。
